# Codebase insights
- 2026-07-04: macOS reprobuild monitoring cannot safely byte-copy Apple
  platform binaries into sandbox tool directories. SIP/system binaries such as
  `/usr/bin/iconutil`, `/usr/bin/hdiutil`, `/usr/bin/sw_vers`, and
  `/usr/bin/codesign` need real non-SIP drop-ins seeded by
  `nim-stackable-hooks` (its rewrite helper only rewrites to existing seeded
  tools) or the build must avoid/cache-disable that action. `io-mon` also has
  two narrow macOS allowances: CFPreferences shared-memory names
  (`apple.cfprefs.daemonv1`, `apple.cfprefs.<uid>v1`) are ambient OS channels,
  and `/dev/fd/N` FIFO aliases must be matched by fd device/inode so inherited
  pipe reads are not misclassified as out-of-tree content.
- 2026-07-04: macOS MCR capture/replay hooks must avoid interpose recursion for
  low-level event primitives. In `ct_interpose`, `dlsym(RTLD_NEXT, "kqueue")`
  and `kevent` can resolve back into the interposed symbol, so use raw syscall
  helpers. For macOS arm64 raw reads, preserve Darwin errno/carry behavior;
  routing through libc `syscall(2)` fixed bogus successful nonblocking reads
  that broke Crystal's signal pipe.
- 2026-07-04: Native-backend Go binary detection must recognize Mach-O Go
  metadata (`__go_buildinfo`, `__gopclntab`, `__gosymtab`) and Mach-O symbol
  spellings with a leading underscore or `.abi0` suffix. The older ELF-only
  section/symbol checks classify macOS Go binaries as `Other`.
- 2026-06-17: `MaterializedReplaySession::type_record` in
  `src/db-backend/src/db.rs` now returns a session-scoped `<unknown>`
  fallback when the supplied `TypeId` is outside both the base reader's
  type table and the local overlay.  Trace formats produced by
  recorders that do not register every typed value (e.g. early JS
  traces that emit `TypeId(0)` for function-bearing locals) used to
  panic the "stable" worker thread mid-`ct/load-locals`, dropping the
  DAP-response channel receiver and stranding the DAP client in
  `pipe_read` on the replay-server's stdout.  The surface symptom was
  indistinguishable from a stdio-bridge deadlock; see the regression
  note in
  `src/frontend/viewmodel/tests/unit/test_formatted_view_step_in_vm.nim`.
- 2026-05-20: `FlowMode::Call` returns the whole enclosing function call's step
  window. For top-level Python code (the `<module>` body) the "call" spans
  the entire script execution, so requesting flow at a breakpoint inside a
  for-loop in `<module>` returns every iteration's steps. `FlowData::values`
  collapses by last-write-wins, which yields the LAST iteration's value, not
  the iteration where the breakpoint actually fired. JS (Node module wrapper)
  and Ruby (`load` semantics) implicitly bound the scope per iteration so
  their HCR tests don't hit this. `tests/python_hcr_ctfs_integration.rs`
  works around it via `extract_var_value_at_stop` which locates the step
  matching the stop's `rr_ticks` and walks forward to the first changed
  `before_values[var_name]`.
- 2026-05-04: `nix develop` and direnv can disagree when `.direnv/flake-profile-*`
  is stale. The current dev shell includes `ourPkgs.sui`; an older cached
  direnv profile may still enter successfully because it references forc/miden/
  cargo-build-sbf but not Sui. Use `nix build --dry-run .#devShells.x86_64-linux.default`
  or clear `.direnv/flake-profile-* .direnv/flake-inputs` before comparing shells.
- 2026-05-04: `nix-blockchain-development-sui` is a temporary cache workaround:
  the upstream nix-blockchain-development input graph had cached Sui 1.68.1,
  while forcing that flake to follow CodeTracer's nixpkgs changed Sui to a local
  GCC 15 build that failed in vendored RocksDB/librocksdb-sys headers. The
  durable fix is to update nix-blockchain-development itself; local testing with
  Sui 1.70.2 and metacraft-labs/nixos-modules b4c1815 built successfully when
  using a large Nix build dir such as `/var/tmp`.
- ViewModel headless tests are organized under `src/frontend/viewmodel/tests/` in three subdirectories: `unit/` (pure VM tests with MockBackendService), `scenarios/` (headless mirrors of GUI tests in `tsc-ui-tests/tests/`), and `integration/` (tests using real replay-server). Every GUI test category has a corresponding scenario file. See `tests/README.md` for the naming convention and mapping table.
- When adding new UI component modules under `src/frontend/ui/`, import them from `src/frontend/ui_js.nim` (the main entry point) so their registration, direct render entrypoints, and IsoNim mount helpers are compiled into the JS output. The old base `Component.render()` fallback was removed during the IsoNim migration; generic render dispatch should not be reintroduced.
- Ruby loops were originally detected only for 'while' and 'until'.
- 'each' loops can be recognized by handling 'call' nodes with a block whose method name is 'each'.
- Added a regression test ensuring `ExprLoader` detects Ruby `each` loops correctly.
- The `tui` crate contains a sample trace under `src/tui/trace/` used for basic testing.
- The Debug Adapter Protocol client communicates over a Unix domain socket using the same framing protocol, implemented in `src/tui/src/dap_client.rs`.
- Pointer address formatting relies on JS `BigInt` via `importjs` for renderer builds, while native builds use standard parsing (`formatPointerAddress` in `src/common/common_types/utils/text_representation.nim`), avoiding Nim-to-JS uint64 quirks.
- Added initial SetBreakpoints handling in db-backend DAP server.
- When using the DAP stdio transport, all diagnostic output must go to stderr
  to avoid corrupting the message stream.
- `src/db-backend/src/main.rs` sends startup diagnostics to stderr (not stdout), and `src/db-backend/tests/dap_backend_stdio.rs` now guards stdio framing with both an initialize-handshake test and a disconnect-response-plus-process-exit test against real `dap-server --stdio`.
- `DapParser` now buffers data via `add_bytes` and exposes parsed payloads with
  `get_message()`, so callers need to drain messages until `None` after feeding
  new bytes.
- `DbReplay::toggle_breakpoint` now mutates its internal breakpoint cache so
  handler state stays consistent after toggles.
- BackendManager now auto-selects the most recently started replay so new DAP
  traffic targets the fresh db-backend without needing an explicit
  `ct/select-replay`.

- Ruby LSP operates diagnostics in pull mode (`textDocument/diagnostic`), and
  only reports semantic issues when a linter such as RuboCop is configured
  (e.g., via `.rubocop.yml` or `linters: ["rubocop_internal"]` in the
  initialize request). Without a linter the server only returns syntax
  warnings, so `missing_helper`-style errors won't surface.


- The db-backend DAP server now responds to the `configurationDone` request.

- Electron lifecycle: the backend-manager process is spawned in
  `src/frontend/index.nim` during `ready()`. Previously, it was only stopped
  via an explicit UI action. We now centralize cleanup with `stopBackendManager()`
  and hook it to `app.on('before-quit')`, `app.on('window-all-closed')`, and
  Node process signals (`SIGINT`, `SIGTERM`, `SIGHUP`) to ensure the process
  is always terminated when the app exits.

- `ct record` resolves Python via env vars (`CODETRACER_PYTHON_INTERPRETER`, `PYTHON_EXECUTABLE`, `PYTHONEXECUTABLE`, `PYTHON`) before checking PATH. When falling back to PATH we now call `findExe(..., followSymlinks=false)` so virtualenv launchers keep their original location and `pyvenv.cfg` remains discoverable.
- Interpreter overrides (e.g. `CODETRACER_PYTHON_INTERPRETER`) are now treated as authoritative; if the configured path cannot be resolved we error instead of silently falling back to PATH.
- `ct record` verifies that `codetracer_python_recorder` is importable before launching the db backend and prints actionable guidance if the module is missing or broken.
- Sudoku test-program datasets include intentionally invalid boards (e.g., examples #3 and #6) with duplicate digits inside a sub-grid; solvers should detect and report these gracefully.
- `ct remote` shells out to `ct-remote`, first checking alongside the `ct` binary and then falling back to the user's PATH if needed; errors are surfaced with actionable messaging when the binary is missing.
- Nix packaging now fetches the prebuilt DesktopClient.App binary, patches its glibc interpreter/RPATH via `patchelf`, and installs it alongside the main `ct`; the devshell, AppImage build (with safe cleanup for `squashfs-root`), non-nix build, and Python wheel build all reuse the same binary so `ct-remote` ships with every distribution path.
- `launchElectron()` uses `execv` on POSIX to replace the ct process with Electron, allowing Playwright to connect via CDP. It sets up `LINKS_PATH_DIR` and `NIX_CODETRACER_EXE_DIR` before execv so the Electron renderer can locate `backend-manager`. The `--inspect` and `--remote-debugging-port` flags are forwarded to Electron.
- The `ct host` CLI expects options in the `--flag=value` form; passing space-delimited values (e.g. `--frontend-socket 1234`) leaves the value empty and the command falls back to default ports, so parallel hosts collide.
- `ct host` exposes a single socket.io listener; keep `--frontend-socket` equal to `--backend-socket-port` when launching multiple hosts so the browser connects to the active socket server.
- In server mode `ct host` registers IPC handlers on the first socket.io client only; after a browser reload/new tab the backend never reattaches listeners, so the fresh socket cannot reach the handler table.
- Server builds now accept `--welcome-screen` so host smoke tests can boot the welcome flow; bootstrap replay requires acknowledging `CODETRACER::started` before the rest of the cached payloads emit.
- Server-mode `mainWindow.webContents.send` now caches bootstrap IPC payloads (started/init/welcome/no-trace/trace load) in `data.bootstrapMessages`; `ipc.replayBootstrap` replays the cache to the latest socket using `bootstrap_cache.nim` ordering.

- 2026-07-30 (RS-M11 remote live request panel over HTTP range): a remote live session really is "the existing `.ct` range reader pointed at a growing file" — `src/db-backend/src/remote_request_spans.rs` produces a `RequestSpanDelta` BYTE-IDENTICAL to the local `RequestSpanTail`'s, and `tests/remote_span_tail_http_test.rs` asserts that equality poll-for-poll, so the frontend has no remote code path. Four traps found building it: (1) **`Content-Length` is NOT a growth signal.** A `.ct` is block-padded — all four RS-M3 tail-stage fixtures are exactly 155648 bytes while `spans.idx` grows 40->56->88->136 — so a remote tail must watch the Block 0 directory's committed `FileEntry.Size` (`CtfsReader::file_size`), never the resource length. The guard is the index's own cumulative column: decoded record count must equal `records_in_chunk`, a mismatch being a hard error when every declared byte landed and a "stop, still landing" otherwise. ## Recording folder shapes: `.ct` is not always a container (M41, 2026-07-30)

`ct` accepts three on-disk shapes for a recording folder, classified in one
place: `src/ct/trace/trace_container.nim::detectTraceFolderShape`.

  1. a `*.ct` CTFS container FILE (magic-checked) — what `ct record` writes;
  2. a materialized `runtime_tracing` directory (`trace.json` / `trace.bin`
     plus `trace_metadata.json` + `trace_paths.json`) — what `ct record-web`
     writes for browser recordings, and what the Rust replay engine has always
     autodetected (`dap_server.rs::auto_detect_materialized_trace_file`);
  3. a `session.toml` multi-recording session manifest.

Two traps this resolves:

  * A **directory** named `foo.ct` is NOT a container. The cross-process
    fixture names its per-process recordings `frontend.ct/` etc., which is why
    `ct host --trace-path <fixture-root>` used to die with "trace folder
    missing `.ct` CTFS container" against a folder that visibly contained
    `backend.ct`. `describeMissingTraceContainer` now names what it found.
  * There used to be two `findCtFileInFolder` implementations with different
    semantics (`storage_and_import.nim` accepted any `*.ct` file;
    `online_sharing/mcr_enrichment.nim` also verified CTFS magic). They are
    unified in `trace_container.nim`; `mcr_enrichment` re-exports it.

Sessions: `ct` never parses `session.toml` itself — it shells out to
`replay-server session <manifest>` (~20 ms) so the only parser is
`db-backend/src/session_manifest.rs`. A session is registered in the recording
index IN PLACE (its `output_folder` is the manifest's directory, not a copy
under `codetracerTraceDir`), because `[[trace]]` paths only resolve next to the
manifest. The GUI needs no per-recording plumbing to open one: the DAP launch
sends that folder as `traceFolder`, and `dap_server.rs::resolve_launch_trace_file`
turns "folder contains session.toml" into a `setup_session` launch.

Beware: `dap_server.rs` has TWO `launch` handlers (the initial one in
`handle_message` and the stable thread's re-launch one). They MUST agree on
trace-file resolution or a session opens as a session on one path and as one of
its members on the other — which is silent, not a crash. Both now call
`resolve_launch_trace_file`.

Which test covers which handler: `cross_process_three_trace_dap_test::
a_session_folder_launches_as_the_whole_session` covers only the STABLE-thread
handler (`task_thread`) — reverting `handle_message`'s call to
`resolve_launch_trace_file` leaves that integration test green. The
`handle_message` half is what the cached-launch flow and tracepoint worker
threads replay, and it is pinned separately by
`dap_server::tests::handle_message_launch_resolves_a_session_folder_to_its_manifest`.
If you touch either handler, run both.

A third `launch` handler exists behind `#[cfg(feature = "browser-transport")]`
(`handle_message_browser`): it re-runs trace detection against the WASM VFS and
OVERWRITES `ctx.launch_trace_file`. `setup_from_vfs` has no session branch, so
that path now refuses a folder holding a `session.toml` outright rather than
latching onto a `trace.ct`/`trace.json` beside it.

Opening a recording MUTATES it, for the CTFS shape only: `importTraceFolder`
runs `materializeCtfsSources(<container>, <source folder>)`, which writes a
`paths.json` **into the folder you pointed at** — including committed fixtures
(`ct host --trace-path .../backend.ct` leaves an untracked `paths.json` in the
fixture). The materialized branch was fixed to normalize the copy in the
recording store instead; the CTFS branch still does it in place because
`importTrace` then copies that sidecar next to the `files/` payload. Discard the
stray file rather than committing it.

Nim test runners cover three roots and `src/ct` was not one of them:
`just test-vm` globs `src/tests/gui/tests/**/*_test.nim`,
`just test-vm-recorder-gated` covers `src/frontend/viewmodel/tests/unit/`, and
(new) `just test-ct-trace-units` covers `src/ct/trace/*_test.nim`. Before that
last recipe every suite under `src/ct/trace` was a test nothing invoked. If you
add a Nim test outside those three roots, add a runner too.

GUI-test flake to know about: `fixtures.ts::importTraceFolder` caps `ct host`
at a 15 s `spawnSync` timeout, and on a loaded machine that trips as
`spawnSync ... ETIMEDOUT` for ordinary CTFS folders too (seen on
`tracepoints_type_error.spec.ts`). It is not specific to sessions.

Not every recorded step belongs to a call. `DbStep.call_key` can be
`CallKey(NO_KEY)` — a FRAMELESS step — and the JavaScript recorder produces them
routinely: three bootstrap steps before `<module>` opens even in a trivial
script, plus one or more at the event-loop level between one callback returning
and the next being entered. Python traces have none. Anything that resolves
`call_key` and treats `None` as an error is wrong on JS traces; that is exactly
what `step_over_depths_step_id` did, which made step-over hold forever at the
last statement of a Node module body (M50). Frameless steps sit at the trace's
OUTERMOST level — `db::OUTERMOST_CALL_DEPTH` — because the `<module>` call and
every callback the loop invokes are all recorded with `depth = 0` and
`parent = NO_KEY`; there is no recorded frame that is shallower.

`step_over_depths_step_id` and `next_step_id_relative_to*` exist TWICE, as
deliberate mirrors: the `TraceReader` trait defaults in `trace_reader.rs` (the
live path — neither `CTFSTraceReader` nor `InMemoryTraceReader` overrides them)
and inherent copies on `Db` in `db.rs`. Change one, change the other.

`TestRecording::drop` does `fs::remove_dir_all(self.temp_dir)`. Never hand-build
a `TestRecording` around a committed fixture to reuse `initialize_and_launch` —
it deletes the fixture from the working tree when the test ends. Use
`DapStdioTestClient::initialize_and_launch_trace(path)` instead.

The tup rule for the db-backend (`src/db-backend/Tupfile`) *names* only
`src/main.rs` as its input, but that is not the whole dependency set: tup
discovers the rest through its FUSE sandbox, recording every file the cargo
invocation actually reads. Editing any file under `src/db-backend/src/` does
re-run the rule on the next `just build-once`, and `src/build-debug/bin/
replay-server` is refreshed — verified by editing `trace_reader.rs` alone and
observing tup execute the rule and cargo emit `Compiling replay-server`. Note
that `just build-once` runs tup twice (before and after webpack); the second
pass legitimately reports "No commands to execute", so read the FIRST pass when
checking whether the engine was rebuilt.

In the Electron build, `dap.nim::asyncSendCtRequest` used to be fire-and-forget:
it wrote the request frame over IPC and resolved the `Future[JsObject]` it
returned with an empty `js{}` immediately, having never seen a response.
Responses arrive on a *separate* IPC channel (`CODETRACER::dap-receive-response`)
and were only fanned out to `dap.on(...)` subscribers. So every
`BackendService.send(...)` in the desktop app resolved with `{}`, and any
ViewModel that read the resolved body silently got nothing — the VS Code build
was fine, because it goes through `activeDebugSession.customRequest`, which
really does return the body. M49 fixed this by correlating on the `request_seq`
the Backend Manager already stamps on every response (`DapApi.pendingResponses`,
settled from `ui_js.nim::onDapReceiveResponse`). If you are debugging a panel
that gets data through events but not through request bodies, this is the
history to know.

`DapApi` is built in four places, and only `dap.nim::newDapApi` uses the named
constructor — `types.nim` and `ui/session_switch.nim` build one from an object
literal per replay session. A field added to `DapApi` and initialised only in
`newDapApi` will be nil on most instances.

`data.dapApi` is NOT one object: it is a template for
`data.sessions[data.activeSessionIndex].dapApi`, so it follows whichever tab is
on screen, and each session's `DapApi` has its own `seq` counter starting at
zero. Anything that has to pair a response with the request that produced it
must therefore pick the session's `DapApi` by the `sessionId` the main process
stamps on the response (`ipc_subsystems/dap.nim::resolveSessionId`), not read
`data.dapApi` — otherwise it silently addresses the wrong session as soon as a
second tab exists. Note also that `ui_js.nim` captures `let dapRef = data.dapApi`
once when it builds the `SessionViewModel`, so the whole ViewModel layer still
talks to the session that was active at bootstrap.

A ViewModel command string needs THREE registrations to reach the wire: a
`CtEventKind` in `common/ct_event.nim`, a non-empty entry in
`dap.nim::EVENT_KIND_TO_DAP_MAPPING`, and a string in
`viewmodel/backend/dap_commands.nim::VALID_DAP_COMMANDS_SEQ`. Miss the first two
and `dapCommandToEventKind` raises `ValueError`, which kills the whole reactive
batch, and the request is never sent — silently, from the caller's point of
view. `scenarios/integration_test.nim`'s "all ViewModel commands are valid DAP
commands" suite is the guard, but it only sees commands the test actually
triggers: a command sent solely from a click handler needs its own case there.

`ct/pairIndexLookup` must be answered at the session layer
(`dap_server.rs::handle_request_via_session`), not by the per-trace `Handler`:
`Handler::build_local_pair_index` sees only its own recording's marker firings,
and a correlation marker's counterpart is by definition in another process.

- 2026-08-11 (Nim ORC's allocator is per-thread, and the region dies with the
  thread — `ct-test test run` SIGSEGV'd at 21+ workers): Nim ARC/ORC gives every
  thread its own `MemRegion`, and that region lives in the thread's TLS
  (`lib/system/mmdisp.nim`: `var allocator {.rtlThreadVar.}: MemRegion`). Every
  string/seq payload is stamped with the allocating thread's region as its
  owner. Cross-thread `dealloc` IS supported — `rawDealloc` sees
  `c.owner != addr(a)` and hands the cell over via `addToSharedFreeList` — but
  ONLY while the owning thread is still alive; that helper dereferences
  `c.owner`. So "protected by a Lock" is NOT sufficient for sharing GC-managed
  data with worker threads: you must also not let worker-allocated memory
  outlive its worker. `run_orchestration.runUnits` returned worker-built
  `RunUnitOutcome`s to its caller *after* `joinThreads`, and the caller's free
  then walked a dangling `c.owner`. It looked fine below 21 workers purely
  because glibc caches retired thread stacks (`stack_cache_maxsize`, 40 MiB
  default) so the dead TLS stayed mapped — silent corruption, not safety. The
  boundary is exact arithmetic, not folklore: Nim gives every thread a 2 MiB
  stack of its own (`ThreadStackSize` in `std/typedthreads` is
  `1024*256*sizeof(int) - 4096`; `ulimit -s` is irrelevant), so 40 MiB holds
  exactly 20 retired stacks and worker 21 is the first whose region is
  unmapped. Then the free segfaults, *after* the run has already printed a
  correct summary (stdout says success, `$?` says 139).
  Two things worth keeping:
  * `GLIBC_TUNABLES=glibc.pthread.stack_cache_size=0` unmaps every worker's TLS
    at join, so this whole bug class becomes deterministic at ONE worker instead
    of probabilistic at 21. Measured on the pre-fix build: exit 139 at
    `--threads 1`, and conversely a 1 GiB stack cache makes the pre-fix build
    survive 64 workers — proof that thread count never made it safe, only quiet.
    Reach for this tunable when stress-testing any threaded Nim code here; a
    clean run without it is close to no evidence at all.
  * `-d:useMalloc` is the independent cross-check: it removes the per-thread
    regions, and the pre-fix build then passes at 64 workers even with the
    cache disabled. If a crash survives `-d:useMalloc`, it is NOT this bug.
  * The fix pattern is in `runUnits`' `ResultHandoff`: workers park on a
    condvar after draining the queue, the spawning thread copies the results
    into its own region and frees the worker-owned originals while the workers
    are still alive, and only then releases and joins them. Any new worker pool
    that returns GC-managed data needs the same hand-off (or `-d:useMalloc`,
    which sidesteps per-thread regions entirely but only protects the binaries
    that are built with it, not library consumers).

    `lexMessage` aborts the process on a malformed literal).

## The caption chrome is rebuilt by every `data.redraw()` (issue #555)

## `array[N, bool]` becomes a `Uint8Array` in the JS backend

Nim's JS codegen represents an array literal of small scalars with a typed
array: `[true, false]` compiles to `new Uint8Array([true, false])`. Any JS
library that validates an option with `Array.isArray()` rejects it.

This is not hypothetical — it silently broke the Omniscience loop slider for
the entire lifetime of the feature. `ui/flow.nim`'s `ensureLoopSlider` passed
`"connect": [true, false]` to `noUiSlider.create`, whose `testConnect` does
exactly that `Array.isArray` check, so EVERY create threw
`noUiSlider: 'connect' option doesn't match handle count.`. `.noUi-base` was
therefore never injected, the `slide` handler was never wired, and because the
throw escaped through `resizeFlowSlider` the rest of that render pass was
abandoned too (issue #562). It now passes noUiSlider's `"lower"` string
shorthand, which means the same thing and survives the translation.

When handing a Nim array to a JS API, prefer a `seq`, a string shorthand the
library documents, or an explicit `{.importjs: "[#, #]".}` helper — and check
the generated `src/build-debug/ui.js` if the API is fussy about its argument
types.

## The VCS panel's infinite-scroll sentinel is a busy loop on small repos

`viewmodel/views/isonim_vcs_view.nim` rebuilds the whole panel subtree inside
one `createRenderEffect`, and the rebuilt subtree ends with a
`.vcs-load-more-sentinel` under a fresh `IntersectionObserver`. On any
repository whose history is shorter than the panel, that sentinel is inside
the viewport the moment it is attached, so it fires `onLoadMoreCommits`
immediately — which used to shell out to `git log` for a page that does not
exist and publish the unchanged commit list anyway, triggering the next
rebuild. Measured at ~60 `git log` processes and ~440 DOM rebuilds per second;
nothing in the panel could be clicked because every element was detached again
before a click could land. `VCSComponent.allCommitsLoaded` now stops the paging
once a short page comes back.

The general lesson: a render effect that recreates an observer, a timer or an
event source must not be able to reach its own trigger. Measure it with a
`MutationObserver` on the panel host — a Playwright "element is not stable" or
"element was detached from the DOM, retrying" failure is what a render storm
looks like from the outside.

## Menu rows carry two class vocabularies, and only one of them is styling

A row in the global menu (`viewmodel/views/isonim_menu_shell_view.nim`,
`menuItemClass`) renders BOTH the design-system component classes
(`ct-menu-item` + `--active` / `--disabled`, styled by
`styles/components/menu_item.styl`) AND a set of styling-free semantic hooks:
`menu-node`, `menu-element` / `menu-folder`, the per-entry identity class from
`node.nameClass` (`menu-folder-debug`, `menu-element-ruby-fibonacci`, built by
`ui/menu.nim`) and `menu-enabled` / `menu-disabled`. The second set is the
published selector contract of the GUI suite —
`welcome-screen/launch_config.spec.ts` and
`codetracer-specs/Testing/UI-Test-Catalog.md` § Launch Configuration Tests
drive the whole Debug > Launch Configurations flow through it.

A pure restyle onto `ct-menu-item` once deleted all of them, which left the
menu looking fine and made every one of those Playwright selectors match
nothing. If you restyle the menu, keep the hooks; and keep them out of
`menu_bar.styl`'s selectors — `#menu .menu-node` outranks `.ct-menu-item`, so
styling a hook silently overrides the component it is supposed to be neutral
about.

mounted exclusively from the `autoHideState.onChanged` callback in
`initLayout`. Anything that mutates the pinned-panel set must go through that
hook, and a test that "forces a strip redraw" with `__ctRedrawAll` is measuring
nothing.

Two consequences worth remembering:

* `onChanged` rebuilds each strip from scratch (`renderAutoHideSideStripInto`
  clears the host and re-appends), so every spurious `onChanged` detaches the
  strip tabs. `locator.hover()` on a tab then fails with "element is not
  stable" / "element was detached from the DOM", and a `toHaveCount` poll can
  land in the emptied window. If a strip tab is unhoverable, look for an
  over-firing `onChanged`, not for a missing render.
* An *open* request must use `auto_hide.revealOverlay`, never `showOverlay`.
  `showOverlay` implements the strip tab's click gesture and toggles, so a
  caller that fires repeatedly (one per search-result batch, one per debugger
  step re-opening the current file) alternates show/hide and drives exactly
  that rebuild loop.

## Collapsed mode makes strip tabs disappear, and Xvfb always looks maximized

`updateCollapsedMode` (ui/layout.nim) decides collapsed mode from
`outerWidth >= screen.availWidth - 8 && outerHeight >= availHeight - 8`. Under
Xvfb the Electron window fills the virtual screen, so the answer is always
"maximized" and the side strips render as a 1 px `collapsed-strip-line` with no
`.auto-hide-strip-tab` at all. `__ctForceCollapsedMode(false)` is now a sticky
override for exactly this reason; before that it was silently overwritten by
the next `resize` event, mid-test.

In collapsed mode the replacement affordance is
`#auto-hide-collapsed-icon-zone` in the status bar
(`Planned-Features/Auto-Hide-Panes.md` §10, "the panel directory").

## The recent-traces list is startup-path state, not welcome-screen state

`Data.recentTraces` / `Data.recentFolders` are global (not session-forwarded)
fields, and the welcome surface of *any* session tab reads them through
`ui/welcome_screen.nim:syncLegacyWelcomeScreenIntoVM`. They used to be filled
only by `ui_js.onWelcomeScreen`, i.e. only when the process was launched into
the welcome screen — so `ct run <program>` left them empty forever and the tab
bar's "+" opened a blank Recent Traces panel (#568).

`src/frontend/index/recent_items.nim` now owns the decision of which startup

`StartupPath` too: `recent_items_startup_vm_test.nim` iterates the enum and
fails if a welcome-capable path delivers nothing.

`findRecentTracesWithCodetracer` and friends `app.quit(1)` on a failed
`codetracer trace-metadata` run; pass `quitOnError = false` from any path that
already has a live debugging session on screen.

## `common_types` types exist TWICE, and a generic proc is how you share code

`src/common/common_types.nim` is `include`d by both `src/common/types.nim`
(`langstring = string`, native) and `src/frontend/types.nim`
(`langstring = cstring`, renderer). Every type in it — `DeepReviewData`,
`Diff`, `Trace`, … — therefore exists as two *distinct* types, and a module
that names one has picked a backend. `state_vm.nim` records what happens when
both end up in scope: "every type in it exists twice and the two copies are
incompatible".

Two ways to write code once and run it against both copies:

1. **A generic proc in a ViewModel module.** `review_entry.reviewDatasetFrom[T]`
   projects a `DeepReviewData` into a plain ViewModel value; the renderer
   instantiates it over its copy, the headless tests over the native one, and
   both run the same source. Read `langstring` fields with `$`.
2. **A proc inside `common_types` itself.** Anything that maps between two
   `common_types` types belongs there — it is compiled once per copy for free.
   `codetracer_features/deepreview_from_diff.nim` (a trace's structured `Diff`
   → a review dataset) and `utils/text_representation.nim` are the examples.
   Convert with `langstring(x)`, which is `cstring(x)` or `string(x)` as
   appropriate.

A headless test *can* `import ../../../../common/types as ct_types` alongside
ViewModel modules (`vcs_vm_test.nim`, `deepreview_entry_test.nim` do); what it
must not do is drag `frontend/types` in as well.

## Review entry has exactly one routine — do not add a second

All three DeepReview launch paths (`ct review`, a trace with an
associated diff, the agentic handoff) publish `data.deepReviewData` and then
call `vcs.startDeepReviewNavigation(data)` → `review_entry.enterReview`, which
populates the VCS panel, the Agent Activity DeepReview section and the editor.
It is idempotent by design: the data half re-runs on every call (the agentic
launcher re-syncs constantly) while the entry half — focus the panels, open
the first file — is gated by `VCSVM.reviewEntered` and the selection is
carried across a refresh *by path*. `src/tests/gui/tests/deepreview/
deepreview_entry_test.nim` holds both a behavioural suite and a source
contract asserting the hosts still call it.

## `ct review` is DeepReview's whole CLI, and it is dispatched in two places

`src/ct/review_cli.nim` holds a *pure* planner, `planReviewCli(argv)`, that
resolves a `ct review …` line into a `ReviewPlan` with no filesystem and no
subprocess. That is what makes the dispatch assertable on both Nim backends
(`src/tests/gui/tests/deepreview/ct_review_cli_test.nim` runs under `nim c`
*and* `nim js`). Everything effectful — resolving the dataset on disk, shelling
out to the native collector — is in the file's `when not defined(js)` half.

The two callers are deliberate and asymmetric:

* `src/ct/codetracer.nim` intercepts `ct review collect|inspect` **before**
  confutils parses argv, because those verbs carry flags that are not ct's
  (`--repo`, `--diff-file`, `--preset`) and confutils rejects any unknown
  dash-prefixed token. Same technique as `ct-complete` and `ct record --`.
* `src/ct/launch/launch.nim` handles `ct review <PATH>` as an ordinary
  `StartupCommand.review`, so it keeps ct's global options (`--inspect`,
  `--remote-debugging-port`) that Playwright injects.

Both call the planner, so they cannot disagree about what a line means.

`reviewNeedsRawDispatch` must key on the VERB alone — `collect`, `inspect`,
`export` — and never on argument count. Claiming the line as soon as a second
token followed the path made `ct review DIR --remote-debugging-port=0` fail
with "exactly one dataset path", i.e. it took back the one property the split
exists to preserve. Extra positionals are confutils' job: it answers them with
"The subcommand 'review' does not accept additional arguments", the same way it
does for `ct edit`.

Retired, and they fail rather than alias: `ct --deepreview <PATH>` (diagnosed
deliberately in `codetracer.nim` — confutils' default names no replacement) and
`ct-native-replay deepreview {collect,export,inspect}` (the group was renamed to
a hidden `review-data` that `ct review` invokes; a hidden `deepreview` arm
survives only to print the pointer). The *frontend* `--deepreview <PATH>`
argument in `src/frontend/index/args.nim` is a different thing and is NOT
retired: it is the internal ct → Electron wire.

`ct review collect --output DIR` writes `DIR/review.json` as well as the binary
`.dr` chunks, because the GUI reads JSON and the `export` step that used to
bridge them is one of the retired commands. `ct review DIR` resolves the JSON
inside the directory.

## Every closure built in a `for` body shares ONE binding — both backends (UD-2)

Nim creates one closure environment per enclosing *routine*, not per loop
iteration, so a `let` in a `for` body is a single slot that every closure built
in that loop captures — each of them sees whatever the last iteration left in
it. Two live bugs came from it in `ui/diff_expansion.nim`: right-clicking the
"show more above" handle opened the "below" menu, and the menu's "Expand 10
lines" item revealed all twelve. The fix is to build each closure in its own
**proc call** (`bindBoundaryHandlers`, `menuItem`), so the captured value is a
parameter of a fresh frame; a `let` inside the loop body is not enough.

Measured on this repo's Nim 2.2.8, at module scope and inside a proc, on BOTH
backends — `nim js` and `nim c` print `@[20, 20, 20]` for the loop-body `let`
and `@[0, 10, 20]` for the proc-call form. This was first written up as a
JavaScript-backend quirk; it is not one, and reading it that way would leave
the same bug unlooked-for in native code. Anywhere a module attaches one
handler (or builds one callback) per element in a loop, look for this first.

A third instance, and the nastiest so far, in `ui/unified_diff.nim` (UD-3): a
`js{ getId: (proc: cstring = widgetId), ... }` built per line in a loop gave
EVERY Monaco content widget the last line's id. Monaco keys `_contentWidgets`
by `getId()`, so `addContentWidget` overwrote one map entry N times while
appending N nodes, and `removeContentWidget` then removed exactly one of them.
The symptom was not a wrong handler but a leak that looked like data: after
stepping the invocation selector once, the previous call's values were still on
screen beside the new call's, 9 bands becoming 16. The fix here is
`udContentWidget`, an `importjs` factory that closes over its arguments in
JAVASCRIPT — worth reaching for whenever a `js{}` literal of closures is built
in a loop, because a proc call in Nim would still have to be written and the
JS factory says what it is.

## A Monaco content widget exists for every line you name; `.view-lines` does not

Monaco virtualises `.view-lines` — only the lines inside the viewport have DOM
— but `addContentWidget` creates the node for any line you register, viewport
or not. Moving the review's inline values from injected text to content widgets
therefore changed what a Playwright query over the whole tab returns: values
from a function scrolled far off screen are now in the document, where before
they simply did not exist yet. `deepreview-gui.spec.ts` Test 30 had asserted
"the text does not contain 55" as a proxy for "line 10 is bare" and started
matching an unrelated `<acc> 55` twenty lines away. If a test asserts the
ABSENCE of something in a Monaco editor, it is probably relying on
virtualisation; name the line instead.

## The diff tab is one pane of a layout, not a window (UD-3)

Measured in the design corpus at 1920x1080: the modified editor's content area
is ~541px and the reviewed file's own annotated lines reach ~495px of it. Any
design that puts something BESIDE the code — the debugger's flow band does,
at `maxFlowLineWidth + distanceToSource` — has very little room here. The flow
panel gets away with it because it owns a whole editor; a review does not, and
a feature ported from one to the other has to measure rather than assume.

## A fit test must ask for the width the CONTENT needs, not for a floor

`ui/unified_diff.applyFlowValueBands` asked `reviewValueBandFitsBeside` for a
twelve-character minimum column before placing the review's value band beside
the code. Nothing is ever DRAWN at twelve characters, so the test answered a
question no band was measured against: on `sample-review.json` at 1920x1080 it
said yes to 210px of room for a column needing 240px, the column was drawn at
its full width 19px past the pane's right edge, and — because the chip budget
came from `available / charWidth div visible` rather than from the column's own
width — the last chip of `<x> 10 <y> 20` was replaced by `…` and a recorded
value left the screen. A floor in a fit test is almost always a bug: ask for
the real number, and if you cannot compute it, that is the finding.

Two more rules came out of fixing it, both general:

  * **A "never draw zero of X" floor needs a companion that clamps X's size.**
    `reviewVisibleColumnCount` always returned at least one column, which is
    right — drawing none reads as "this line never executed" — but on its own
    it is what drew a column that did not fit. `reviewDrawnColumnChars` caps
    the width; the pair can then never put anything outside its container.
  * **Give up whitespace before you give up a placement.** The obvious remedy
    for "it does not fit beside the code" is the fallback placement, and here
    that is a Monaco VIEW ZONE, which adds its own height to the document.
    Moving all nine of the fixture's bands there cost ~315px in an 896px pane,
    pushed the file's line 23 out of the viewport and turned four unrelated
    expansion tests red. Shrinking the band's GAP instead
    (`reviewValueBandLeftPx`'s three-argument form) costs nothing at all: no
    code moves, no line hides, no chip drops, and the single left rail holds.

## A loop's columns are sized per LOOP, not per line

`FlowComponent.calculatePositionMaxWidth` raises
`loopState.defaultIterationWidth` over EVERY position of the loop and every
iteration at it, and `renderFlow` lays every line of the loop out against that
one number. So pass 2's column starts at the same x on every line of the loop.
UD-3's review band first sized per line, and the consequence was not only
misalignment: a narrow line fitted more passes than a wide one, so the loop's
header row showed four passes above body rows showing one, and a reviewer read
that as "missing 3 of 4 passes' data". `reviewLoopColumnChars` is the per-loop
maximum, and it is the debugger's rule rather than a review-specific one.

## `ensureFlowLoopSlider(requireMeasurable)`: "never build at zero width" needs a way back

#562's lesson is real, but it is only half a rule: refusing to construct until
an element is measurable is safe exactly when somebody comes BACK. `ui/flow.nim`
in EXTENSION mode has no such path — `resizeFlowSlider` is reachable only from
`doRenderActiveLoopIterationValues` behind `if not data.self.inExtension`, from
`resizeEditorHandler`, which needs an `editorUI.monacoEditor` the extension does
not have, and from `ui/editor.nim` — so a refusal there is permanent and the
VS Code / browser extension simply never grows a slider. That is why the shared
`flow_loop_slider.ensureFlowLoopSlider` takes `requireMeasurable` and
`ensureLoopSlider` passes `not self.inExtension`. Any guard of the form "not
ready yet, come back later" needs the *later* proved for every host, not just
for the one being worked on.

## Monaco's overlay widgets are painted UNDER the code (UD-2)

`.monaco-editor .lines-content` has `z-index: 2` and `.overlayWidgets` has
none, so a widget in the overlay layer — which is where the diff editor's
`hideUnchangedRegions` boundary lives — loses the hit test to `.view-line` at
its own centre. Measured with `document.elementFromPoint`. The lift has to go
on `.diff-hidden-lines-widget`, not on a child: `.diff-hidden-lines` carries a
`transform`, which makes it a stacking context that a child's `z-index` can
never escape.

## `hideUnchangedRegions` will collapse a `@@` divider (UD-2)

The divider is an unchanged line of both models and sits directly before the
hunk's own leading context lines, which are unchanged too — so with
`contextLineCount: 3` the three lines kept visible are the hunk's context and
the divider is hidden. `diff_document.diffContextLineCount` derives the option
from the document (longest divider-to-change tail, plus one) instead of fixing
it at three.

## A deleted line's colours come from a zone built ONCE, before the tokens exist (UD-4)

Monaco's inline diff draws each deletion as a `view-lines line-delete` view zone
inside the *modified* editor and builds it from the ORIGINAL model's tokens —
`oe.originalRange.mapToLineArray(n => Ae.tokenization.getLineTokens(n))` in the
shipped bundle. `getLineTokens` returns whatever tokenization has already
reached; nothing in that computation observes token changes, so the zone is
never rebuilt when they arrive. UD-1 diagnosed the flat `mtk1` deleted lines as
missing tokens and recorded `experimental.useTrueInlineView` as the only fix.
Both halves were wrong. Measured in the running product:

  * the tokens are present — the original model's `  let y = x * 2;` reports
    nine tokens with foregrounds `[1,23,1,25,1,25,1,34,25]` — while the zone
    rendered from it is a single `mtk1` run;
  * forcing tokenization earlier changes nothing, before or after `setModel`;
  * invalidating the DIFF rebuilds the zone, and the rebuilt one is coloured.

So the recipe is: wait for a zone to exist, then invalidate the diff *once*
while the zone is monochrome (`ui/unified_diff.scheduleDeletedLineTokens`).
`renderIndicators` does NOT work as the invalidation — the zones follow the diff
result, not a rendering option; toggling `ignoreTrimWhitespace` and restoring it
in the same synchronous block does.

Corollary for tests: a span in a deleted zone carries `char-delete` as well as
its `mtk<n>`, so collecting whole `className` strings counts `"mtk1"` and
`"mtk1 char-delete"` as two token classes and passes on a document with no
tokens at all. Match `/\bmtk\d+\b/`.

## `tup` can miss a `.nim` edit, and the build then lies quietly (UD-4)

`just build-once` reported "No commands to execute" against a freshly edited
`src/frontend/ui/unified_diff.nim`, and the Playwright suite then ran green
against the previous build — which is the worst possible outcome for a
red-before-green step, because the test passes for the wrong reason. `touch`ing
the edited file made tup rebuild it immediately. After editing frontend Nim or
styl, `touch` the file before building, and confirm the compile actually
happened (`frontend/ui_js.nim` in tup's output) rather than trusting exit 0.
Note also that `src/public/dist/frontend_bundle.js` is the *vendor* bundle
(Monaco et al.) — the renderer's own code is `src/build-debug/public/ui.js`, so
grepping the bundle for your change proves nothing.

## `.code-editor .flow-loop-step-container` absolutely positions whatever wears it (UD-4)

`ui/flow.renderFlow` marks the selected loop pass with `flow-loop-step-container
active-flow-step`, and any host that copies that convention inherits
`text_editor.styl`'s `position: absolute; width: 3.125em; margin-right: 0.625em`
along with the highlight — because in the debugger's own band the columns are
placed by computed offsets. In a flex band (the review's value row) that is both
the wrong width and out of the flow, and the symptom is subtle: only the rows
that contain a loop start on a different left edge from every other row. Reach
for the class for the highlight, and neutralise the layout in your own scope.

## The Monaco theme had no `diffEditor.*` colour at all (UD-4)

`codetracerDark.json` styled the editor and the brackets and nothing about a
diff, so every unified diff CodeTracer has ever drawn wore Monaco's `vs-dark`
defaults — a saturated crimson removal against a desaturated olive addition,
which three independent reviewers measured as unbalanced. The keys worth knowing
are `diffEditor.{inserted,removed}{Line,Text}Background`,
`diffEditorOverview.{inserted,removed}Foreground` and, for the collapsed-region
band, `diffEditor.unchangedRegion{Background,Foreground}` — that last pair is
the supported way to colour the "N hidden lines" band, which otherwise ignores
any colour set on `.diff-hidden-lines .center` alone.

## The fold widget is 34px of content in a 0px box, straddling two code rows (UD-4)

`.monaco-editor .diff-hidden-lines` is `height: 0; transform: translateY(-10px)`
with a 24px `.center` and two handles stacked inside it, and the widget is an
*overlay* widget, so the stack is painted across whatever is rendered above and
below the fold. Measured: the last code line occupied y 483..505 and the band
came out at 501..525. Moving the offset only trades the overlap from the line
above to the line below — five reviewers across three milestones reported one or
the other. The fix is to make the whole stack fit one code row (two 3px handles
plus a 16px band = 22px) and zero the transform. Monaco's own
`diff-hidden-lines-compact` variant is an 11px text row, so a compact band is
its idiom rather than a shrink. Note also that the widget is drawn in BOTH
editors, and the original one is a ~30px gutter strip — that slice of a
full-width control is the "unexplained mark at the far left of the fold" three
reviewers inventoried.

## The diff gutter's gap takes TWO declarations, and neither works alone (UD-4 audit)

`text_editor.styl`'s global `.line-numbers` rule is `width: 100% !important;
box-sizing: border-box; text-align: right !important`, so in the diff editor
that element is not the numbers COLUMN — it is the whole margin, and its right
edge is where the code starts. Two consequences that cost a milestone each:

  * a `padding-right` is the only thing that holds the digits off the code, and
  * it only holds while the label still fits the box the padding shrinks.

Monaco sizes the margin as `lineNumbersMinChars` x its own
`typicalHalfwidthCharacterWidth`, and `diff_document.lineNumberLabels` emits a
label of exactly that many characters, so the label always overflowed the padded
box and spilled back to the right (an overflowing line box ignores `text-align`
in `ltr`) — measured, glyphs `292..317.7` against code at `321`, a 3.3px gap
that four reviewers called a collision while a `padding-right: 0.9em` sat in the
stylesheet apparently answering them. The lane (`lineDecorationsWidth`, MODIFIED
editor only — the original strip cannot afford it) buys back exactly what the
padding spends. Keep the two numbers equal: if a font ever renders wider than
Monaco's estimate the text overflows again and the gap degrades to the lane's
width rather than to nothing.

## Monaco's `.diff-hidden-lines .center` is a FLEX container (UD-4 audit)

So a `::after` on it is a flex item: `vertical-align` does nothing at all, and
`align-items: normal` means an item with no height STRETCHES to the flex line
(the pseudo-element resolved to the band's own 24px) while an item with a height
falls to the start of the line. The `expand` pill sat ~6px above the band's text
for that reason, through two rounds in which `vertical-align: middle` looked
like it was placing it. Use `align-self`, and give the pill a `height` equal to
its `line-height` so its box is its line box.

## `.margin-view-overlays div` is painted by `text_editor.styl` (UD-4 audit)

Every child of a margin overlay gets the panel colour from a two-element
selector, which outranks a bare decoration class — so a `marginClassName` whose
CSS is a single class silently paints the panel colour instead. Scope the rule
under `.monaco-diff-editor .modified-in-monaco-diff-editor` and it both wins and
stays on the side you meant: both models carry the `@@` line, so an unscoped
rule also paints the original editor's 29px strip.

## Equal alpha is not equal weight, and neither is equal luminance (UD-4 audit)

The add/remove washes were argued about by five reviewers across four
milestones, because "heavier" was never defined and the three candidate measures
disagree. Composited over `#282828`, `#7FC085` and `#E06C75` at the same alpha
are equal in CIEDE2000 (10.59 / 10.49) and in chroma (7.5 / 8.2) and 1.54x apart
in relative luminance. Equalising the luminance with alpha made two fresh
reviewers report the opposite defect within one round, because at a fixed hue
dE and dL grow together — their RATIO is a property of the hue (0.43 for that
green, 0.66 for that red) and no alpha pair can match both. Changing the hue is
the lever: `#408050 @0x30` matches `#E06C75 @0x26` on all three measures at
once. Measure a wash as the COMPOSITE against the surface it lands on, on all
three axes, before changing a number.

## A nil mock-DOM lookup used to kill the whole `isonim_views_test.nim` binary

FIXED — kept because the shape recurs in every file that hand-rolls
`findByClass` over `isonim/testing/mock_dom` (about fifteen of them).

What it was: `findByClass` returned nil when nothing matched, and essentially
every caller dereferences the result on the next line. `unittest`'s `check`
does NOT abort a failing case, so `check n != nil` reported the failure and the
line after it dereferenced the nil. A nil `MockNode` deref is a SIGSEGV, and a
SIGSEGV kills the process: the file declares 461 cases, the native lane
reported 216 (212 OK + 4 FAILED), and **245 cases — 53% — produced no result at
all**, AA-1's `no DeepReview roll-up` guard among them. It was a cascade, not
one line: guarding the first site moved the crash to the next, same shape.

The fix, and the reason it is NOT `require`: `std/unittest`'s own `require`
sets `abortOnError`, so `fail()` ends in `quit(1)` — it kills the process just
as the segfault did. `unittest`'s `test` template wraps each case body in
`except Exception:`, so a raised CatchableError is the primitive that fails one
case and lets the rest run. `findByClass` / `findById` / `findByTag` in
`views/isonim_views_test.nim` therefore RAISE `MockNodeNotFoundError`, and the
handful of assertions whose subject is absence use the `…OrNil` spellings. Both
lanes now report the same result over the same case count — 465 OK, 0 FAILED.

The 17 that used to fail were NOT a property of the raising lookups: they were
cases still written against the pre-redesign Find in Files DOM (and one against
a button size class that moved). They were re-expressed against what the view
emits today, so "17 known-acceptable failures in `isonim_views_test.nim`" is no
longer a thing; a failure here is a real one.

The runner half: `test-vm-native` tested `fails > 0` before it tested the exit
code, so the SIGSEGV printed as `PARTIAL (212 OK, 4 FAILED)` — indistinguishable
from an ordinary partial run. All six compile-and-run lanes now classify
through `ci/lib/test-lane-report.sh`, which reads the exit status FIRST;
`ci/test/test-lane-report-test.sh` proves it against fixture processes that
print plausible `[OK]` lines and then die.

To run one case: `./isonim_views_test "<exact test name>"`. The filter is an
exact match on the test's own name, not a glob and not a substring, and it
matches nothing against suite names.

## `configureMiddleware` does not run in a `ct review` launch (AA-2)

`ui_js.configureMiddleware` is called only from `onTraceLoaded` and
`onNoTrace` — the handlers for `CODETRACER::trace-loaded` and
`CODETRACER::no-trace`. A `ct review` dataset launch reaches neither:
`index/startup.nim` sends `CODETRACER::start-deepreview` and returns, so
`onStartDeepReview` is the only one of the three that runs. Everything wired
inside `configureMiddleware` — including the whole `initPanelVM`
block that installs the shared ViewModel store into the legacy panels — is
therefore absent in review mode. Anything a review needs must be installed from
`ui_js.configure`, which runs once per renderer in every launch mode. Symptom
to recognise: a panel that renders correctly in a review but whose actions are
silent no-ops, because the host service it calls through was never installed.

## Nested render procs inside an `ui(r):` block build nothing (AA-2)

The IsoNim DSL nests *tags*. A bare call to another `render*` proc inside a
`ui` block evaluates, builds a node, and attaches it to nothing — the parent
renders empty with no error. Take a container with `ref = host` and
`r.appendRenderedChild(host, renderChild(r, ...))` after the block, the way
`isonim_agent_workspace_view` and `isonim_agent_activity_view` do.

## The sharing path is now kind-parameterised, not trace-shaped (AS-1)

`src/ct/online_sharing/artifact.nim` holds the artifact model: a closed
`ArtifactKind` enum (`recording`, `review-dataset`), a `const
array[ArtifactKind, ArtifactKindSpec]` registry indexed BY THE ENUM (so a new
kind that skips its row does not compile), and the one URL grammar every path
in `api_client.nim` is now derived from.

Two things that surprise people reading it:

* The recording kind's URL segment is `traces`, not `recordings`, and that is
  permanent. Every share URL the service has issued and every path the shipped
  client sends contains it. `artifact_model_vm_test.nim` pins the generated
  strings against string *literals* for that reason — regenerating the
  expectation from the registry would agree with any rename.
* The user-facing share URL — `/{orgSlug}/{id}/download` — carries NO kind.
  That is what made the generalisation cheap, and it is why
  `parseArtifactShareUrl` must never infer a kind from the URL shape.

The module is deliberately free of filesystem, HTTP, `Trace` and `langstring`
so it compiles on `nim js` too; `common/recording_id.nim` was split for the
same reason (`isCanonicalUuidV7` is backend-neutral, `newRecordingId` is
behind `when not defined(js)` because it needs the OS CSPRNG).

`ArtifactProtection` has exactly one value, `apNone`. There is NO encryption
and NO password protection anywhere on this path — AS-3 adds them. A test
asserts the enum's cardinality so widening it has to be deliberate.

## Nim test lanes are DISCOVERED now, and a guard keeps them that way

Lanes used to enumerate by name, and a name list omits silently. Measured

were reached by NO lane — every `src/ct_test/incremental/test_*.nim`, all

* `ci/test/test-lane-coverage.sh` — the guard. "Test-shaped" has TWO arms and

  Every test-shaped file must be in a lane or declare, IN ITSELF, that it is

  `## NOT-A-TEST-LANE-FILE: <reason>` in its first 40 lines, or a

## Two-argument `parseEnum` is a FALLBACK, not a validator (fixed; do not reintroduce)

`parseEnum[E](token, default)` silently substitutes `default` for anything it
does not recognise and never raises, so a `try`/`except ValueError` around it is
dead code. `artifact.parseArtifact` used it for `visibility`, `minimumWriteRole`
and `protection`: `"public"` read as `avTenant`, `"owner"` read as `arMember`
(fail-OPEN), `"aes-256-gcm"` read as `apNone`. AS-2 replaced all of them with
`parseClosedEnum` / `readClosedEnumField` in `artifact.nim` — exact matching, no
fallback arm, a refusal naming the token and the closed set. Use those for any
new closed set that comes off the wire.

Two adjacent holes of the same shape, also closed: `getStr()` on a NON-STRING
JSON value returns `""`, which fed straight into the fallback (so
`{"visibility": 7}` read as `tenant`), and the payload's `layout` had the same
problem. And keep ABSENCE distinct from an unknown value: a record written
before a field existed genuinely does not declare it, so an absent `protection`
must still read as `apNone` or every wire-format addition becomes a breaking
change.

## `ct upload` / `UploadedInfo` — what the modern path can and cannot answer

Fixed by AS-2; the shape is worth knowing because the reasons are wire facts,
not code style.

* `uploadTrace` RETURNS now; it used to end every path in `quit(...)`, which
  made `uploadCommand`'s success output — and the machine-readable JSON line
  `src/frontend/index/online_sharing.nim` parses — unreachable. If you add a
  path here, return from it.
* `UploadedInfo` carries `artifactId`, `kind`, `shareUrl`, `uploadSessionId`.
  It used to carry `fileId` (the recording id after a single-file upload, the
  SESSION id after a slice upload — one field, two namespaces) plus
  `downloadKey` / `controlId` / `storedUntilEpochSeconds`, which are the
  pre-M-REC-8 service's tokens that nothing on the modern path assigns.
* **A sliced recording gets no share link, and that is correct.** The recording
  kind's `…/upload-session` body is frozen to `{platform, recordingMode}` and
  carries no artifact id, so the client never tells the service which recording
  the session is for — the service names the result itself.
  `ArtifactStoreOutcome.serviceAcknowledgedId` records whether it named it back,
  and a link is printed only when it did.
* The platform is `artifactPlatformToken(hostOS, hostCPU)`, not the literal
  `"linux-x86_64"` it used to be on every machine. An untaught host pair yields
  `""` — an absence, never a guess.

## `totalSlices` counts PIECES, not uploaded objects (AS-2; a caught regression)

The `/finalize` body's `totalSlices` is what the deployed CS-M7 service
**reassembles the payload from**. A sliced recording uploads its `.smnf` /
`.amnf` manifests through the same session, at indices after the slices, and
the pre-AS-2 client deliberately did not count them. So `ArtifactPart` carries
an `ArtifactPartRole` (`aprSlice` / `aprSidecar`) and the finalize body is
built from `sliceCount(parts)`, never `parts.len` — on the normal
`ct-mcr record --split` output those differ by two, and sending the larger tells
the service to look for slices that do not exist.

Two lessons worth more than the fix:

* **A wire test must state what the PREVIOUS client sent, not what this one
  computes.** The first draft of AS-2 shipped this regression with two suites
  that both asserted `totalSlices == parts.len` — tautologies against the
  implementation, green on the bug. They are now driven by a named directory
  (`McrSplitDirectory`) and a literal `3`.
* **Diff at the CALLER, not just the builder.** Every URL and every body
  builder was byte-identical to `e356c20f`; the regression was in what the
  caller passed the builder. `src/ct/online_sharing/` is verified by running
  the real `uploadSplitTrace` against a recording HTTP server in both trees and
  diffing the request log.

## The sharing transport is ONE path, keyed on payload LAYOUT (AS-2)

`src/ct/online_sharing/` splits into a pure planner and a native executor:
`artifact_transfer.nim` produces the whole conversation (every URL, every body,
every part, in order) as a function of the artifact and the local files;
`artifact_store.nim` executes it and is the only place in the repo that moves an
artifact's bytes. `storeArtifact` dispatches on `ArtifactPayloadLayout`
(single-file vs slice set) and NEVER on `ArtifactKind`, which is what lets a
review dataset use the slice transfer that was built for recordings.

Two rules to keep:

* The recording kind's request bodies and URLs are **frozen** — a deployed
  service reads them, and `artifact_transfer_vm_test.nim` asserts their exact
  key sets against literals. Adding a key there is a wire change.
* `slice-upload-url` and `finalize` are keyed on a SERVER-issued session id, so
  their collection segment comes from `ArtifactUploadSession` (the typed pair
  `…/upload-session` returns), not from a literal and not from a kind supplied
  again at the call. Revert that and a sliced review dataset publishes its parts
  under `traces/`.

## `ct download` probes a route that does not exist yet — be careful with 4xx

`fetchArtifact` asks the kind-neutral `artifacts/{id}/download-url` BEFORE the
kind's alias (AS-1 §5.4), and no deployed service routes it. So every existing
user's download now begins with a request that fails, and what a service says
about a path it has no rule for is not under our control — a gateway or WAF may
answer 400, 403 or 501 as readily as 404. `downloadProbeMayContinue` therefore
tolerates all of those ON THE NEUTRAL PROBE ONLY; a kind's own collection
continues on 404/405 alone, because a 403 there is a real "you may not read
this" and walking past it would report a permission problem as a missing
artifact. 401 never continues, on either.

## The sharing surface is ONE value, and it is the only place sharing copy lives

`src/ct/online_sharing/artifact_sharing.nim` (AS-4) produces every sentence
`ct upload`, `ct download` and `ct list` show about sharing, derived from the
artifact model. It is pure and compiles on `nim js`, which is why the *claims*
(what encryption covers, who can read what you shared) are asserted in the
ViewModel lane without a socket.

Per-kind variation may enter through FIVE doors and no more: the noun
(`artifactSubjectNoun`), the kind's own facts (`artifactFacts`), the open
command (`artifactOpenCommand`), §10.4's visible-metadata list
(`describeVisibleToService`), and `accessApiNotices`. If you find yourself
wanting a sixth, you are adding a second sharing flow — the thing this
milestone removed, where four separate success blocks described one upload.

**Know where the guarantee stops.** It covers the sharing VIEW — what the user
is told about the artifact. It does NOT cover `upload.nim`'s narration about
moving the bytes (`MCR trace with pre-split slices detected`, `Uploading N
pre-split slices`, `Upload finalized: N slices`, the progress lines). Those
differ per PAYLOAD SHAPE, not per kind, and they are declared in an allowlist
that `sharing_flow_cli_test.nim` enforces against a real upload of each kind —
including a genuinely sliced recording, so the list is driven and not merely
written. A new line printed on one path only fails until somebody declares it.

**The equality is asserted at THREE layers, and know why.** `sharingShape`
strips the doors from the VIEW; `kindNeutralRenderedLines` strips them from
`renderSharingView`'s TEXT; and the JSON comparison strips them from
`sharingViewJson`. As AS-4 first shipped, only the first existed — and a door
added to the renderer, gated on one kind and one stage, left every suite green
while the pre-AS-4 wording came back in the product. A guarantee about a value
is not a guarantee about the output built from it. The normaliser is pinned too,
because widening it is the next hiding place, and it lives in the TEST rather
than beside the renderer for the same reason. Note WHICH pin does the work: an
earlier version claimed "removals must account for exactly that many lines",
which is a tautology for any reconstruction whose lines each appear once, so it
could not detect widening at all. Two things actually hold it. The reconstruction
is built from the view's OWN neutral fields, so it can only absorb a line whose
rendered text equals the field-derived text -- the instant that line differs per
kind, `line in rendered` fails. And `doors.len == expectedDoorLineCount(view)`
counts from the view's DECLARED doors, independently of how the reconstruction
builds them, so the two must agree from different sources.

Related: assert every STAGE. The gated door survived because the CLI suite
compared line-for-line only at `assOffered`; `assShared` was JSON-only and
`assReceived` was compared for neither kind. Downloading a *recording* needs a
real CTFS container (`importTrace` reads its `meta.dat`), which is why that
whole path had gone unexercised — `src/tests/cli/sharing_flow_cli_test.nim`
now builds one with `m1_ctfs_fixture`.

Two rules that are easy to break by accident:

* **Do not state a fact the client was not told.** No deployed service returns
  an artifact record, so `sharingView(..., accessKnown = false)` is what
  `ct download` passes; without it the view printed the model's DEFAULT
  visibility as though it were the artifact's. `ct list` has the same rule
  under a different name (`ListingLocalOnly`). The same class one step over:
  `accessApiNotices` is gated on the STAGE, because "CodeTracer recorded this
  locally and the service was not told" is false after a download and
  contradicted the "not stated" lines directly above it.
* **`confutils` eats options you will swear you passed.** A bare `--flag` and
  `--flag=` never reach the command for a value-taking option — the same defect
  as AS-3's `--password-file -`. `artifact_crypto.bareDashInArgv` and
  `optionGivenWithoutValueInArgv` read `argv` for exactly this, because by the
  time a parsed value exists the token is gone. `libs/nim-confutils` is pinned;
  refuse client-side. **And look at the NEIGHBOUR**: a bare `--flag` is only
  value-less when it is last or the next entry starts with `-`. The first
  version of that guard matched the token alone and refused
  `--visibility tenant-or-invite`, the conventional spelling, which had
  worked — under-firing and over-firing are the same mistake seen twice.
* **`ct download`'s non-tty stdout is consumed WHOLE.**
  `src/frontend/index/online_sharing.nim`'s `onDownloadTraceFile` takes
  `$res.value.strip()` as the imported recording id, so the non-interactive
  branch must print the locator and nothing else — AS-4's notices go to
  **stderr** on that path for exactly this reason. `ct upload` is different:
  its consumer scans back for the LAST non-empty line, so narration before the
  JSON is harmless.

## In-process sqlite does not load outside the test-lane runner

`import db_connector/db_sqlite` compiles, then dies at process start with
`could not load: libsqlite3.so(|.0)` unless the run inherits
`CT_LD_LIBRARY_PATH` (the lane runner exports it for the RUN step; a bare

## A `set -e` lint script only runs as far as its first red step

`ci/lint/*.sh` used to be flat lists of commands under `set -e`. That shape has
one failure mode and it is not small: the FIRST failing command decides how much
of the job ever runs, and everything below it is documentation.

Measured, not theorised:

* `ci/lint/bash.sh` aborted at line 8 on a shellcheck SC2001 *style* finding in
  `ci/test/desktop-capabilities-dispatch.sh`. Behind it sat
  `scripts/resolve-sibling-rev-test.sh` (89 assertions) and
  `tools/visual-review/deepreview-harness-test.sh` (65 contracts). Both pass
  when run by hand — which is exactly why nobody noticed they had never run in
  CI. 154 assertions, green in principle, unexecuted in practice.
* `ci/lint/nim.sh` aborted at line 10 on a crashing `just test-nimsuggest`, so
  the test-lane coverage guard below it had never executed either. The guard
  built to catch "tests that do not run but look like they pass" was itself an
  instance of the class.

The fix, and where to look:

* `ci/lib/lint-steps.sh` — `lint_step "<literal name>" cmd...` runs each check in
  a subshell, records the verdict, and ALWAYS returns 0, so a red step cannot
  abort a caller running under `set -e`. `lint_summary` prints one verdict line
  per step and decides the exit status from all of them. A step exiting **78**
  is QUARANTINED: reported and counted, but not fatal. The library uses shell
  builtins only, on purpose — see the guard.

  **Do not "simplify" that to `("$@") || rc=$?`.** Bash suppresses errexit
  inside any command that is an operand of `||`, and A SUBSHELL INHERITS THE
  SUPPRESSION — re-issuing `set -e` inside does not re-arm it:

      $ bash -c 'rc=0; ( set -e; false; echo reached; true ) || rc=$?; echo $rc'
      reached
      0

  So a step body that is a shell function running several commands under
  `set -e` reports only its LAST command's status. Caught in review with two
  failing `cargo check --release -D warnings` runs reporting OK and
  `ci/lint/rust.sh` exiting 0 — strictly worse than the flat script the library
  replaced, which at least aborted loudly on the first one. The fix is to turn
  errexit off around a PLAIN call and restore it afterwards (`case $- in *e*)`),
  which has no such inheritance. `ci/test/lint-step-isolation-test.sh` case
  "a multi-command body under set -e" pins it; note that Part B cannot, because
  making every command fail also makes the last one fail.
* `ci/test/lint-step-isolation-test.sh` — the guard for the class. Part A is the
  library's contract suite. Part B RUNS every `ci/lint/*.sh` with `PATH` pointing
  at a directory containing nothing but `dirname`, so every step fails, and
  asserts each script still exits non-zero, still prints its summary, and still
  names every step it declared. Pass old scripts as arguments to see it go red:
  the pre-fix `bash.sh` dies at its first command and never mentions the other
  eight checks. It also runs the lint scripts against a throwaway copy of `ci/`
  with cwd inside it, because `ci/lint/rust.sh` writes files.
* Order still matters, for a different reason: put pure-bash/git guards ahead of
  anything needing a compiler so their answer reaches the log sooner. They just
  no longer HIDE what follows.

## nimsuggest crashes on this repo's `config.nims`, not on its Nim code

`just test-nimsuggest` has been red on the pinned toolchain (Nim 2.2.8). It is
not a CodeTracer regression, and the recipe's old advice (chronicles log
statements over distinct types) does not apply:

* A one-line `echo "hi"` file placed in the REPO ROOT crashes nimsuggest exactly
  as `src/lsp.nim` does. The same file outside the repo is fine.
* `nim check` on that file, under the same config, is clean — the compiler front
  end is fine and only the nimsuggest driver is affected. All of `--v1`/`--v2`/
  `--v3`/`--v4` crash identically.
* `--skipProjCfg` makes it disappear, and copying `config.nims` alone into an
  empty directory reproduces it. It is the NimScript config, not the sources.
* It is memory corruption, not a deterministic error: the same input yields
  either SIGSEGV or `AssertionDefect: the length of the seq changed while
  iterating over it`, and which one depends NON-MONOTONICALLY on how many
  unrelated config lines precede it (truncated at 102 passes, at 110 asserts, at
  129 segfaults; a shorter prefix plus the same trailing block passes again).
  Deleting a config block "fixes" it only by moving the heap around.

So it is quarantined rather than deleted, and the quarantine narrows itself:
`ci/test/nimsuggest-check.sh` re-runs nimsuggest on a probe file it generates
itself. Probe also crashes -> exit 78 (QUARANTINED). Probe clean but `src/lsp.nim`
crashing -> exit 1, because that is the real regression the check has always
existed to catch. Nothing has to remember to un-quarantine it.

## `echo "$x" | sed 's/^/    /'` -> `printf '    %s\n' "${x//$'\n'/$'\n'    }"`

shellcheck flags the sed form (SC2001) and the rewrite IS equivalent on
multiline input, which is worth knowing because it is the case where you would
expect it not to be: the parameter expansion indents every embedded newline and
the format string supplies the first line's indent. Blank interior lines and an
empty value match too, and command substitution has already stripped trailing
newlines. The printf form is strictly safer — `echo "-n"` prints nothing.
`print_indented` in `ci/test/desktop-capabilities-dispatch.sh` is the shared
helper.

## `libs/parsetoml` does not compile against the pinned Nim 2.2

Anything that needs to read TOML from Nim has to bring its own reader.
`libs/parsetoml/src/parsetoml.nim:1725` compares two `seq[TomlValueRef]`, and
seq equality is a `func` that cannot call parsetoml's own side-effecting
`proc ==`:

    comparisons.nim(324, 6) Error: '==' can have side effects

The path IS on the search path (repo-root `config.nims:34`) and nothing under
`src/` imports it, which is why this had never surfaced. It is also a pinned
submodule, so patching it from this repo would leave a dirty submodule.
`src/ct_test/certificate.nim` carries a ~250-line reader for the TOML subset
test certificates and key stores use — strict on purpose, because a key store
that cannot be read has to be reported as unreadable rather than silently
degraded.

## `ct test run` has never been able to run a Nim or Python test

`canRunProject`/`canRunFile`/`canRunSingle` are all `false` for `nim-unittest`,
`python-pytest`, `python-unittest` and every `smart-*` provider — they discover
only. The providers that really run today are the C/C++, Go, D, Crystal, Rust,
Ruby, JS and M12-fallback ones; `js_node_test` is the cheapest way to get a
genuinely green `ct test run` on a dev box (a `node:test` file, no install).

Such a run used to report `executed: N` (units dispatched) with
`passed: 0, failed: 0` and **exit 0**. Both halves are fixed:
`run_orchestration.runUnitOutcome` now refuses to dispatch to a provider whose
declared `canRunScope` is false — recording a `dsError` and
`RunUnitOutcome.unrunnable` instead of calling the stub `run` that returned a
warning nobody read — and `runVerdict` distinguishes three outcomes, so
`ExitNothingExecuted` (2) is what a run that finished no test now exits with.
See "the `executed` field means TESTS" below.

This matters to certificate issuance: a run with no finished tests attests
nothing, so `src/ct_test/certificate_issuance.nim` withholds rather than
issuing an empty claim, and `certificate_cli_test.nim` uses exactly that
property to exercise the withheld path with no toolchain at all.

## Private fields do not make a builder unforgeable

Nim rejects `Obj(privateField: x)` from another module, so it is tempting to
treat "all fields unexported" as a capability boundary. It is not: an exported
mutator that fills those fields is a way to fill them. `certificate_issuance`
shipped exactly that shape for a day — a private-field `AttestedRun` plus four
exported mutators, one of which (`recordUnitResult`) took a caller-supplied
`seq[TestEvent]` — and a caller could obtain a real, `ssh-keygen -Y verify`-valid
test certificate for tests that never ran. The suite's own `passingRun` helper
was that forgery, which is why nothing went red.

The shape that does hold: **a routine that runs the tests does not take the
results as arguments.** `runAndAttest` calls `runUnits` itself; the record and
its mutators are unexported. When you need "only this module may build X",
unexport the type AND the mutators, and expose one entry point that produces
the value from something it computed.

Two guards worth copying, both in `certificate_issuance_test.nim`:

* A `compiles()` check is **vacuously true** whenever its expression fails to
  compile for any reason at all — a typo passes just as well as a private
  symbol. Put a positive control next to it (`check compiles(<exported call>)`)
  or the check proves nothing.
* An exported-surface allow-list must scan `template` and `macro`, not only
  `proc`. A proc-only version stayed green while
  `template signAnyBlob*(p, k) = signCanonicalPayload(p, k)` handed another
  module the private routine.

## `tsSkipped` is a fourth outcome, and "not failed" is not "passed"

`TestResultStatus` has four values, and `summarize` in run_orchestration.nim
counts a skip as neither passed nor failed — correct for a run summary, and a
trap for anything downstream that gates on `failed == 0`. `ct test`'s
certificate issuer did exactly that and, for a suite where every test was
skipped, issued a signed certificate asserting `result = "passed"`; for the
much commoner mixed suite it added the skipped file to the certificate's
`targets`, claiming coverage for a file that executed no assertion.

Three shipped providers reach this from the DEFAULT registry, all honestly:
`frameworks/ruby_common.nim` maps rspec `pending` -> `tsSkipped`,
`frameworks/js_common.nim` maps node:test's TAP `# SKIP`/`# TODO` the same way,
and `frameworks/js_playwright.nim:263` maps `skipped`. So any consumer of the
event stream that means "a test ran" must test for
`tsPassed | tsFailed | tsErrored` explicitly rather than for `not tsFailed`.
`certificate_issuance.recordUnitResult` is the worked example.

And know how far that gets you. **THREE providers report skips per test on
their run path: `js-playwright`, `ruby-rspec` and `js-node-test`.** Each one
had to stop reading a subprocess exit code to get there, because all three
runners exit 0 for an all-skipped suite:

* `js-playwright` -> `--reporter=json` -> `statusFromPlaywright`.
* `ruby-rspec` -> `--format progress --format json --out FILE` ->
  `parseRspecJsonResults` -> `statusFromRspec`. The `--format progress` is
  load-bearing: `--format json --out FILE` alone REPLACES the terminal
  formatter (rspec installs a default only when none is configured, and a
  file-bound one counts), so stdout goes silent — measured against rspec 3.13,
  `.rspec`'s own `--format documentation` included.
* `js-node-test` -> node's TAP stream, parsed by `parseNodeTapResults`. NO
  command flag: `node --test` picks `tap` whenever stdout is not a TTY, which
  under `ct test`'s capture is always, and `--test-reporter` does not exist
  before Node 18.15. What guards the assumption is a cross-check of the parsed
  tallies against node's own `# tests` / `# pass` / `# fail` / `# skipped` /
  `# todo` counters; a mismatch falls back to the exit code with a warning
  rather than being believed. Under-counting is the dangerous direction --
  zero events read as "nothing executed" and would WITHHOLD a certificate that
  should have been issued.

The remaining providers still derive a whole file's status from one subprocess
exit code (`cpp_common`, `native_m11_common`, `m12_fallback_common`,
`smart_contract_common`, and `ruby_common`'s minitest branch), so a skip is
indistinguishable from a pass there. The rest of the registry -- jest, vitest,
pytest, python-unittest, nim-unittest, rust-libtest -- has no `run` wired at
all (`unsupportedRun` / a not-implemented stub), so it reports no finished
test and can claim nothing; do not read it as a third category of gap.

Minitest shares `runRubyCommand` with rspec and deliberately does NOT get a
JSON path: it has no equivalent reporter, so `buildRubyCommand` is handed an
empty results path for it and its command is byte-identical to what it always
was. One proc, one branch on the framework kind — not a fork.

`grep -rln tsSkipped src/ct_test/frameworks/` is still the WRONG evidence -- it
answers "which files mention the token", not "which providers can emit it from
`run`". Both a previous version of the certificate docs and a verification pass
drew a false conclusion from that one grep (rspec USED to carry a correct
`pending -> tsSkipped` mapping whose only caller was a unit test of itself).
Follow `provider.run` to the proc that decides status. Any per-test property
enforced downstream is bounded by that, and saying so is the difference
between a guarantee and a hope.

Related, same file: a unit whose provider returns diagnostics and NO
`tekTestFinished` (crashed harness, missing toolchain) contributes nothing to
either count. That used to exit 0; it no longer does — see below.

And the counters read `tekTestFinished` ONLY: `tekFailure` is invisible to both
`summarize` and `recordUnitResult`. `runRubyCommand`'s failure branch used to
emit a `tekFailure` and no `tekTestFinished`, so a workspace in which every
Ruby test FAILED reported `executed 0, failed 0` and exited 2
("nothing-executed"), not 1 — a real failure reported as an absence. Measured
on a one-method failing minitest project before the fix. If you add a provider
branch that means "this did not pass", the `tekTestFinished` is the part that
counts; the `tekFailure` beside it only carries the reason.

## The `executed` field means TESTS, and the exit code has three outcomes

`TestRunSummary.executed` (JSON `executed`) counts `tekTestFinished` events
whose status is `tsPassed | tsFailed | tsErrored` — the SAME definition
`certificate_issuance.AttestedRun.executed` uses. A `tsSkipped` test counts in
`skipped` and NOWHERE else: a skip runs no assertion and is not evidence.
`passed + failed == executed` is a real invariant.

It used to mean *units dispatched*, which is why a run that handed out 333
units and finished zero tests printed `"executed": 333` and exited 0 while the
certificate path withheld with `wrNoTestsExecuted` — the exit code and the
attestation contradicting each other inside one binary. The dispatched count
still ships, as `dispatched`; it is always `total - skipped_by_partition`, so
redefining `executed` cost no consumer any information.

`runVerdict` → `runExitCode`, checked in that order:
- `failed > 0` ⇒ `rvFailed` / exit 1 (unchanged).
- else `executed == 0` ⇒ `rvNothingExecuted` / exit **2**. Covers an
  all-skipped run, an allow-list that matched nothing, and a dispatch no
  provider could run — one verdict, four messages, because they need different
  remedies but support the same (empty) claim.
- else exit 0.
The verdict is also emitted as the summary's `verdict` key, and
`run_orchestration_test.nim` pins that the field and `$?` never disagree.

A run that executed SOME tests and had SOME unrunnable units stays green
(partial coverage is normal — the certificate issues for one too) but reports
`unrunnable`, a per-provider `errors` array, and a stderr warning. If you want
that to redden, it is a policy change, not a bug fix.

No consumer outside this repo reads this schema: reprobuild's readers
(`repro_cli_support.summarizeTestResults`, the `ct_test_unittest_parallel`
suites) expect the standalone `repro_test_runner`'s NESTED `{"summary": {…},
"tests": […]}` shape — a top-level `summary` object CodeTracer's flat document
has no key for, so those readers see `(0, 0)` / `{}` rather than misreading it.
And nothing can invoke this CLI as that runner anyway: reprobuild resolves
`CT_TEST_RUNNER` / a `ct-test-runner` on PATH / `repro_test_runner`, none of
which codetracer produces (the standalone `ct-test` binary is built ad hoc by
`ci/test/m16-release-gate.sh` into a cache dir and installed nowhere), and it
invokes it as `run --bin-dir=… --summary-json=… --results-dir=… --no-build
<binaries>` — every one of which `parseRunArgs` rejects as an unknown argument.
The two runners have never been wired to each other.

## `ct test` discovery is bounded by the workspace root you name (and used to
## depend on your shell's CWD)

Every "where is repository X?" question in ct_test goes through ONE proc,
`workspace_scope.siblingRepoInWorkspace(workspaceRoot, repoName)`: either the
root IS that repo (`--workspace codetracer-cairo-recorder`) or it CONTAINS it
as a sibling checkout (`--workspace <multi-repo workspace>` — the usual
invocation, and the one `m13_smart_contract_harnesses_test.nim` exercises with
`getCurrentDir().parentDir`). Nothing above the named root is searched and
`getCurrentDir()` is never consulted. Its three callers are
`smart_contract_common.findRecorderRepo` (which decides which fixtures become
test units) and the JS/Ruby recorder-prefix resolvers (which decide which
binary records a trace). Do not reintroduce a private copy — all three had the
same cwd seed and all three lost it for the same reason.

It used to also walk up from `projectRoot.parentDir` **and from
`getCurrentDir()`**, and `fixtureFiles` then enumerated whatever sibling repo
that found. Measured before the fix, same `--workspace` (a scratch dir holding
one rspec project), same binary, only the CWD differing:

    cd ~                            → 1 catalog,  11 items
    cd .../prox-fixes/codetracer    → 15 catalogs, 341 items

The 330 extras were `smart-{cairo,move,evm,solana,fuel,miden,circom,leo,
polkavm,ton,cardano,flow,wasm,wasmi}` fixtures under the sibling recorder
repos. All three cwds now answer 11. `--scope`/`--unscoped` never affected
this either way: workspace scoping constrains the workspace walk, not the
recorder-repo enumeration.

Related invariants worth knowing before touching any of it:

* `item.file` is relative to the **workspace root** for every provider,
  `smart-*` included (it used to be relative to the recorder repo). Both
  consumers resolve it against that root — `run_orchestration.scopeForItem`
  builds the absolute path the provider is invoked on, and
  `certificate_issuance.targetOfUnit` names it as what the run covered — so a
  repo-relative spelling silently pointed at a non-existent file and would
  have had a certificate claim `test-programs/…` of a repo with no such path.
* Containment is one shared, resolved (not spelled) test:
  `workspace_scope.workspaceRelativePath` / `isInsideWorkspace`, used by
  `discovery.boundToWorkspace` (which drops out-of-workspace items from a
  workspace discovery and warns) and by `targetOfUnit`. Keep them sharing it;
  discovery enumerating what attestation refuses to claim is exactly the
  defect above.
* KNOWN GAP: the registry's stored `TestProvider.info.capabilities` for
  `smart-*` is computed by `newSmartHarnessProvider` with `projectRoot = ""`,
  so its `canRunFile` can only see `<SPEC>_CMD` and `PATH`, while
  `runRecorderCommand` re-resolves from `scope.projectRoot` and also accepts
  `<repo>/target/{debug,release}/<binary>` — the location `just
  build-siblings` produces and nothing in this tree exports. Since
  `runUnitOutcome` gates dispatch on the stored value, a workspace whose
  recorder was built but not installed gets a catalog advertising
  `canRunFile: true` and every unit refused as `unrunnable`. Deterministic
  now (it used to vary with the CWD too), but still wrong. Fixing it needs a
  projectRoot-aware capability hook the provider interface does not have: the
  registry is built once before any workspace is known and is caller-supplied,
  and gating on the catalog's capabilities instead would contradict
  `run_orchestration_test`'s "a provider that declares it cannot run is never
  dispatched to".

## Which recorder binary the JS and Ruby providers use, and why the answer is
## NOT what `scripts/detect-siblings.sh`'s name suggests

`js_common.jsRecorderCommandPrefix` and `ruby_common.rubyRecorderCommandPrefix`
each take the workspace root and try, in order:

    JS    CODETRACER_JS_RECORDER_PATH  →  PATH  →  <workspace>/codetracer-js-recorder/packages/cli/dist/index.js (via node)
    Ruby  CODETRACER_RUBY_RECORDER_PATH →  <workspace>/codetracer-ruby-recorder/gems/…/bin/…  →  PATH

The two orders differ on purpose (a Ruby recorder shipped in the workspace
matches the Gemfile the tests were written against); only the *starting
directory* of the workspace step is shared. Both used to start it from
`getCurrentDir().parentDir`, and Ruby additionally from `currentSourcePath()`
five parents up. Measured before the fix with one workspace, one file and one
environment, varying only the cwd, the same call answered three ways for JS —
the workspace's own recorder, "codetracer-js-recorder is required", and an
UNRELATED sibling checkout's recorder — and two ways for Ruby, the second
being the recorder beside the *source tree the binary was compiled from*.

Two things that will mislead you:

* **`detect-siblings.sh` does NOT export `CODETRACER_JS_RECORDER_PATH` or
  `CODETRACER_RUBY_RECORDER_PATH`.** Both variables are honoured by the code
  and neither is set by the dev shell. What the script actually does is
  prepend a directory to `PATH`: the recorder's `gems/…/bin` for Ruby (works),
  and `node_modules/.bin` for JS — which `npm install` never populates when
  the workspace's `node_modules` comes from a read-only Nix derivation, so in
  that configuration nothing puts the JS CLI anywhere findable and the script
  warns. `scripts/build-siblings.sh` says the same thing at :313-325. The
  block comment at `detect-siblings.sh:330` describes materialising a shim
  under `<repo>/.bin/`; it does not do that either. Until one of those is
  fixed, a JS *recording* test must name a workspace containing the recorder
  checkout (what `js_providers_test.nim`'s CommonJS recording test now does)
  or set the env var itself.
* Do not "fix" it by putting the JS recorder on `PATH` from the dev shell
  without checking the lanes: `ci/test/cli-record-smoke.sh:166` skips its
  JavaScript case on `command -v codetracer-js-recorder`, so making it
  resolvable changes the `cli-record` lane's counts.

Neither prefix proc can put a sibling path anywhere durable. It reaches only
the argv, the `tekRecordStarted` message and `TraceMetadata.metadata
["recordCommand"]`; `item.file` comes from discovery (always
`normalizedRelative(projectRoot, …)` over `walkWorkspaceFiles(projectRoot)`),
and `certificate_issuance.targetOfUnit` reads `unit.item.file` alone. Both
providers' `TestCapabilities` are compile-time constants, so — unlike
`smart-*` — recorder availability does not move their catalogs either. The
blast radius is capability, not attestation: the same workspace could record
from one shell and refuse from another.

## The Embed SDK facade and its import lint (2026-08-28)

`src/frontend/viewmodel/codetracer_embed.nim` is the CodeTracer Embed SDK's
entire public surface (CodeTracer-Embed-SDK.md §7: "anything not exported from
the Nim `codetracer_embed` module is private"). If you are adding something a
consumer needs, add it there; if you are refactoring something not exported
there, you are not making a breaking change.

Two things about it that will otherwise surprise you:

* **`ci/test/sdk-facade-boundary.sh` is a build gate**, wired into
  `ci/lint/nim.sh`. It walks the facade's transitive import graph lexically —
  and that walk was validated to be *byte-identical* to `nim c --genDeps` for
  the C backend (32 modules), so treat a disagreement as a bug in the
  resolver, not in the rule. It fails on rendering/DOM/layout in the graph,
  on `std/osproc` in the graph, and on any chain concept (`chainId`,
  `blockNumber`, `txHash`, …) anywhere in it. The chain rule is §3.2's newest
  row and the one under real pressure, because BlockTracer is the first
  consumer.
* **A file becomes a "consumer" only by declaring itself one**, with a
  `## SDK-CONSUMER: <reason>` header or a `.sdk-consumer` file in an ancestor
  directory — the same two spellings `ci/test/test-lane-coverage.sh` uses. A
  declared consumer may import `codetracer_embed` and nothing else from
  `src/frontend/viewmodel/`. An undeclared file is unconstrained.

Two limits of that guard, both deliberate and both worth knowing before you
trust it further than it goes:

* **`src/frontend/ui/` is banned by PATH, with a one-entry allowlist**
  (`UI_PATH_ALLOWLIST`), and the reason is written up at length in the script.
  The short version: the rule was briefly deleted on the argument that the
  import graph subsumes it, and that argument is false. `ui/flow_line_styles`,
  `ui/editor_decoration_layers` and `ui/trace_redraw_policy` have **zero
  imports** and are presentation policy — the first exports `"line-flow-hit"`
  and friends — so they present to an import-graph rule exactly as the
  genuinely-pure `ui/flow_loop_math` does. If the ban fires on you, add your
  module's exact path to the allowlist with a reason; do not widen the rule.
* **The graph walk does not enter IsoNim.** It checks this repo's modules plus
  the *first-level* external specs they name, so "no rendering in the SDK
  graph" means "none in this repo, and none at IsoNim's entry points". A
  rendering dependency added inside IsoNim would not move this lint. That is
  benign today — the compiler's own dep list for the facade reaches only
  `isonim/core/*`, `isonim/viewmodel` and `isonim/testing/test_utils` — but it
  is unguarded, and IsoNim is a peer package on someone else's release
  cadence.

Related, and easy to get wrong:

* `viewmodel/vm_log.nim` exists because `frontend/lib/logging` imports
  `lib/jslib`, which imports `dom` and `kdom`. Eleven `[PIPELINE]` debug lines
  in `store/replay_data_store.nim` and `viewmodels/calltrace_vm.nim` were
  putting the Karax DOM shim into the SDK's `nim js` graph. Use `vmDebug` in
  the ViewModel layer; `cdebug` is fine everywhere in the renderer.
* `sdk/debugger_session.nim`'s `newDebuggerSession` builds the store but NOT
  the panel VMs: `session_vm.initializePanelViewModels` is called by
  `launch`/`attach`, because several panel VMs own effects that issue backend
  requests and there is nothing to ask about before a trace is open.
  `app_vm.createAppViewModel` grew an `initializePanels` parameter for this;
  it defaults to `true`, so existing call sites are unchanged.
* `headless_session.HeadlessDebugSession` is now a *host* around a
  `DebuggerSession` rather than an owner of its own graph. It still does its
  own DAP handshake, because it needs `DapStdioBackend.waitForEvent` and
  `BackendService.onEvent` is a registration, not a pump — the stdio
  adapter's `onEventProc` collects handlers and never calls them.

## The degraded-state catalogue is split across two packages (BlockTracer M2b)

`BlockTracer/Page-Descriptions.md` §14 lists thirteen degraded states and ends
with the rule that each is "a value of an enum on a ViewModel, not a branch in
a view". The table reads as one list; it is not.

* **Seven of the thirteen rows are chain-level** — pipeline behind the tip,
  object not found, trace awaiting generation, recorder unavailable for the
  VM, transaction below the history floor, reorganised away, CDN unreachable.
  They belong to BlockTracer's own ViewModels (`ChainVM`, `TraceStatusVM`,
  `GenerationJobVM`, ... — Front-End-Architecture.md §3). Modelling one of
  them in `src/frontend/viewmodel/` violates CodeTracer-Embed-SDK.md §3.2's
  last row and trips `ci/test/sdk-facade-boundary.sh`'s chain-token scan.
* **Six reach a pane** and live in `viewmodel/store/degraded_state.nim`:
  replay window expired, permanently unreplayable, browser cannot run the
  debugger, trace truncated, divergence detected, no verified source.
  That module's header carries the full row-by-row ownership table.

The split is 7-up/6-down for *modelling*, but it is NOT 7-up/6-down for
ownership, and reading it that way is the trap. Four of the six also have a
BlockTracer ViewModel named against them in Front-End-Architecture.md §3 —
`CapabilityVM`, `DivergenceVM`/`TraceStatusVM`, `SourceBundleVM`/`AddressVM`,
`ArtifactVM`. Those establish the condition from inputs that are chain- or
delivery-shaped (a capability probe, a manifest verdict, a provider chain, a
retention policy); the enums here are what a *pane* renders. The seam is
`ReplayDataStore`'s four setters plus the `CtReplayStatus` event: above
writes, panes read. Neither layer is redundant, and deleting `CapabilityVM`
because "the SDK already has `CapabilityRung`" would be the wrong conclusion.

Shape worth keeping if you extend it:

* ONE `PaneDegradation` enum plus a per-pane `set[PaneDegradation]`, not one
  enum per pane. §14 asks for "one canonical treatment rather than being
  reinvented per page"; five enums would be five places to re-decide what
  "truncated" means and to re-derive the precedence between two simultaneous
  conditions — the branch-in-a-view failure moved up a layer.
* The precedence is data (`DegradationPrecedence`), not control flow, so a
  test asserts the ordering directly.
* `DebugControlsVM.replayUsable` gates every `can*` memo. A step button that
  is enabled over a replay that cannot run IS the "retry that cannot succeed"
  §14 forbids, so the gate belongs in the memo and not in the view.
* Degraded state reaches the store over a `CtReplayStatus` backend event as
  well as through host-side setters, so `MockBackendService.emitEvent` can
  drive every §14 row headlessly. Unrecognised wire spellings deliberately
  leave the signal alone rather than falling back to the healthy default.

## `ci/test/sdk-facade-boundary.sh` needs bash >= 4 — it now handles this itself

It uses `mapfile`, which macOS's /bin/bash 3.2 does not have. The script now
re-execs into the first bash >= 4 on PATH, so no caller has to arrange it, and
if there is genuinely none it prints `NOT RUN   bash-version: ...` and exits
**2** — reserved for "could not run", as against 1 for "found something".

The old advice here was "run through `direnv exec <repo> bash -c '...'`, which
supplies bash 5", and it was **half wrong in a way that cost real time**. Being
inside the dev shell is not sufficient: `bash -lc` re-sources the profile and
puts /bin ahead of the nix store, so on this machine `direnv exec … bash -lc`
got **3.2** and `direnv exec … bash -c` got **5.3**, same shell, same moment.
The login flag was the variable, not the dev shell.

What it cost: `test_sdk_facade_boundary.nim` shells out and reads the exit
status, so under 3.2 it reported FOUR content failures — including
`VIOLATION consumer-facade-only`, its own negative control — for a checker
that had not run. That was both of `ci/lint/nim.sh`'s FAILEDs and the only red
in `just test-vm-unit` on a clean `cloud`, i.e. a gate that was red everywhere
locally and therefore read by nobody.

## The ViewModels and the wasm32 replay engine speak different DAP dialects

`src/frontend/viewmodel/backend/dap_dialect.md` is the measured, reproduced
record — eight disagreements, four of which trap the WASM worker. Read it
before wiring any pane to `WorkerBackendService`. The three that bite first:

* **Handshake order.** `sdk/debugger_session.nim:377-383` sends `initialize ->
  configurationDone -> launch`; the browser engine needs `launch` before
  `configurationDone`, because `handle_message_browser`'s `configurationDone`
  arm (`dap_server.rs:2743-2775`) is the only place the `Handler` is ever
  constructed and it reads a folder only `launch` populates. Get it wrong and
  all three requests answer `success: true`, then every later request is
  dropped with a bare `warn!` (`dap_server.rs:2809`) — no response, so the
  future hangs forever. The NATIVE path tolerates both orders; the browser
  path's copies of both tolerances are inert because they are `&&`-chained
  onto `ctx.to_stable_sender`, which is `None` in the browser.
* **`SystemTime::now()` traps on wasm32.** No cfg guard, no shim; `vfs.rs`
  works around it for the VFS only. `ct/load-locals` (so the State pane cannot
  work at all), `ct/originChain`, any step reaching a trace boundary, and
  `disconnect` all die. `probe_engine_defects.mjs` reproduces all four.
* **`drainPlatformCallbacks()` cannot see a real transport.** On JS,
  `onComplete` uses the drainable queue only for `__syncResolved` futures —
  i.e. `newCompletedFuture`, i.e. `mock_backend`. Anything built with
  `newPromise` and resolved later (`worker_backend`, `real_backend`) is
  observed by a `.then` microtask a synchronous drain cannot pump. This site
  has now been wrong twice for two different reasons; commit `caaea86c` fixed
  the synchronous half only.

## Two dispatch tables, and neither is in `dap_handler.rs`

`dap_handler.rs` has no `match` on a command string at all — it holds the
handler methods. The tables are `dap_server.rs:2043` (`handle_request`, the
full command set) and `dap_server.rs:2676` (`handle_message_browser`, which
handles only initialize/launch/configurationDone/disconnect and delegates the
rest to `handle_request`). Grepping `dap_handler.rs` for command-looking
strings matches filesystem paths (`meta_dat/sources`, `origin-patterns`), a
replay-task name (`"flow"`) and a default literal (`"source"`) — none of them
commands.

## The browser's Build/Run path, and four things that were quietly in its way

- 2026-09-01: `ui/web_noir_build.nim` is the call path from a gesture to the
  Noir wasm toolchain. Everything either side of it existed and was tested
  (registry, worker protocol, transport, the merged NS9 bundle); nothing
  called it. Marshalling is `platform/noir_build.nim`, pane-driving is
  `viewmodels/noir_build_producer.nim`, and both are pure so `vm-unit` and
  `vm-unit-js` run all of it. Four obstacles were found by measurement and
  each is worth knowing before touching this area:
  * **`ui/shortcuts.nim`'s hard-coded `ctrl+b` shadows a CONFIGURED shortcut.**
    `default_config.yaml` binds `build: "CTRL+B"`, the YAML loop binds it, and
    then a later `Mousetrap.bind` in the same proc replaces it — Mousetrap
    overwrites rather than chains. The YAML entry has been dead on every
    platform. It is now excluded from `-d:ctWeb`, and the web arm installs
    `data.actions[ClientAction.build]` instead, which `bindShortcut` reads AT
    PRESS TIME. A `Mousetrap.bind` from `ui_js.nim`'s web arm does NOT work:
    `onNoTrace` is `{.async.}` and calls `configureShortcuts()` again in a
    later microtask, so it rebinds over anything installed there — measured,
    with `Mousetrap.trigger('ctrl+b')` from the page also reaching nothing.
  * **The generated entry document had the auto-hide STRIPS and not the
    OVERLAY.** BUILD, PROBLEMS, FIND IN FILES and REQUESTS are standalone
    auto-hide panes (`ui/layout.nim`): their DOM lives in
    `#auto-hide-standalone-host` at `left:-9999px` and revealing one means
    reparenting it into `#auto-hide-overlay-content`. `web_deployment.nim`'s
    skeleton omitted `#auto-hide-overlay`, so `doShowOverlayImpl` logged
    "not found in DOM" and returned — none of the four could ever be opened in
    a browser. The skeleton now carries the overlay, the backdrop and the three
    docked hosts, copied structurally from `src/frontend/index.html`.
  * **`build.syncLegacyBuildIntoVM` wiped the pane on every reveal.**
    `ui/layout.nim`'s `onPanelShown` calls it whenever the BUILD overlay is
    shown, and it is a BULK REPLACE from `self.build` — the Electron
    producer's mirror, permanently empty in a browser. Measured: a compile
    reporting `rows=1 paneRows=1` (one view model, holding the row) and
    `#build` holding none 50 ms later, the row appearing only on the next
    gesture. It now returns early when the legacy record is empty and the view
    model is not.
  * **`wasm_worker.finish` dropped a `failed` message's TEXT on the `start`
    path.** `run` gets it as a `PlatformError.message`; `start` has no
    `settle`, so the three module-load faults
    (`not-delivered`/`not-served`/`broken`) reached a streaming caller as a
    bare exit code 1. It is now delivered on stderr before the exit.
- 2026-09-01: `mode: "debug"` SILENCES WARNINGS. `compiler/wasm/src/vfs.rs`'s
  `debugging_compile_options()` sets `silence_warnings: true` (nargo's own
  choice — the instrumenter imports `__debug` functions the user did not
  write). Measured over one program carrying both an unused expression and an
  unresolved path: `program` mode reports 2 diagnostics, `debug` reports 1. So
  Build asks for `program` and Run asks for `debug`, and they are not

- 2026-09-01: a counted assertion does not save you from an empty set. The
  all-files sweep asserts verdicts == manifest entries, and that agrees
  perfectly at zero: testing the step on macOS, `find -printf` is an unknown
  primary, the manifest came out EMPTY, and the step printed
  "ok: 0/0 published files match what was uploaded" for every host and exited
  0. Nothing was wrong and nothing was checked. Two fixes, both needed: the
  manifest is now built with `-exec sh -c ... +` (portable, so the same block
  runs on the workstation), and the floor is asserted by NAME — `index.html`
  and `ui.js` must appear in the manifest, because a manifest built from the
  wrong directory has neither and a bare `> 0` would not notice.

## Watch expressions: seven places, and the wire was always carrying them

- 2026-09-04: `CtLoadLocalsArguments.watchExpressions` has existed on both
  sides of the wire for as long as the State pane has, and the frontend has
  always populated it. There was never a missing feature to design — there
  were seven disconnected pieces, each of which reads as success from the
  others' point of view. Anyone touching this area should know all seven:
  * **`db.rs` dropped the field with a `warn!`** ("watch expressions not
    supported for db traces currently"). The request carried the expression
    and the response carried no row for it AND no reason, so the pane could
    not tell "not evaluated" from "no such variable".
  * **`state_vm.nim`'s `currentVariables` memo returned a literal empty seq
    for `stWatches`**, with a comment promising it would be filled in "when
    the backend supports them". The tab could show nothing whatever the
    backend answered.
  * **The WebRenderer panel in `isonim_state_view.nim` had no tab strip.**
    The Locals/Globals/Watches buttons existed only in the *MockRenderer*
    panel in the same file, which is what the headless view tests render —
    so `stWatches` was reachable from `vm.selectTab` and from no gesture in
    any shipping product. A test that switched tabs through the ViewModel
    passed against a product no user could navigate.
  * **The typed expression and the answered request were on different
    objects.** The live input form (`wireWatchInputForm`) calls
    `StateVM.addWatch`; the reply the product paints comes from
    `StateComponent.loadLocals` -> `CtLoadLocalsResponse` ->
    `registerLocals`, and `loadLocals` read `StateComponent.watchExpressions`
    — a field written only by `submitWatchExpression`, which has NO CALL
    SITES anywhere in the repo. `ui/state.nim` now sources the list from the
    ViewModel and installs `onWatchesChangedProc` to re-ask.
  * **`replay_data_store.requestLocals` keyed its dedup on the COUNT of
    watch expressions**, so swapping one watch for another at the same step
    was suppressed and the pane kept answering a deleted expression.
  * **`headless_session.requestAndLoadLocals` hardcoded
    `"watchExpressions": []`** while the same file exposes `addWatch` /
    `removeWatch` — the identical crossed wiring on the SDK surface.
  * **The page objects located `#watch`; the view renders `#watch-0`.**
    Both `layout_page.ts` and `variable-state-pane.ts` had a locator that
    has never matched an element. Nothing caught it because no spec ever
    typed into the box.
- 2026-09-04: **do NOT route watch evaluation through
  `tracepoint_interpreter`**, which is what `db.rs`'s TODO pointed at. It is
  gated behind the `syntax-highlight` feature (it compiles expressions with
  tree-sitter) and `src/db-backend/build_wasm.sh` builds the browser engine
  with `--no-default-features --features browser-transport`. In that build
  `TracepointInterpreter::evaluate` is the stub in `tracepoint_interpreter/
  mod.rs` that returns `vec![]`. Using it would ship a feature that works on
  the desktop and silently answers nothing in a browser — the same defect
  one layer down. `watch_expression.rs` therefore depends on nothing but the
  trace's own value records and answers identically in both builds.
- 2026-09-04: a REFUSED watch travels as `ValueRecord::Error { msg }`, not
  as a new wire field. The Nim `Value` already has an `Error` kind whose
  text representation is its `msg`
  (`common_types/utils/text_representation.nim`), so a refusal renders as a
  visible row on every existing frontend without any of them learning a new
  case. `Value.isWatch` — declared in `common_types/language_features/
  value.nim` and styled `.value-watch` since before any backend wrote it —
  is what separates a watch row from a local; the Rust `Value` gained the
  matching `is_watch` field.
- 2026-09-04: watch rows are appended to `locals` AFTER the sort and dedup
  in `Db::load_locals`, deliberately. Sorting them in would scatter them
  through the list in name order, and the dedup (`a.expression ==
  b.expression`) would DELETE a watch whose expression equals a local's
  name — which is the most ordinary watch anyone types.
